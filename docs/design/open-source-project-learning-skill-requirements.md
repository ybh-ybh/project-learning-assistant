# 开源项目学习 Skill 需求文档

## 1. 文档信息

- 文档状态：初稿
- 当前版本：v0.2
- 创建日期：2026-09-04
- 最近更新：2026-09-04
- 目标项目：`project-learning-assistant`
- 目标产物：一个帮助用户系统学习本地开源项目的 Codex Skill

## 2. 背景

用户希望通过一个可复用的 Skill，将已经下载到本地的开源项目转化为结构化、循序渐进的 Markdown 课程。适用的开源项目例如：

- `deepseek-ai/deepseek-harness`
- `TencentCloud/TencentDB-Agent-Memory`
- `langchain4j/langchain4j`

GitHub 等代码托管平台的项目链接可以作为项目来源信息，但不是本 Skill 分析源码的输入依据。用户应先将项目下载到本地，Skill 必须根据本地项目目录中的实际文档和源码生成课程。

已有的 TencentDB Agent Memory 学习资料整体效果符合预期，可作为本 Skill 的设计参考：

- 参考目录：`D:\programData\ObsidianLib\Java技术\开源项目学习\TencentDB-Agent-Memory`
- `agent.json`：用户与 OpenCode 的完整交互记录
- `00_课程大纲.md`：课程大纲示例
- `01_设计哲学与整体认知.md` 至 `10_团队权限模型与全链路串联.md`：分课学习文件示例

参考资料用于提炼课程组织方式和内容质量标准，不应成为 Skill 运行时只能处理 TencentDB Agent Memory 项目的限制。

## 3. 建设目标

该 Skill 应当：

1. 确定用户希望学习的本地项目目录及课程偏好。
2. 在生成内容前识别缺失的必要信息，并向用户集中澄清。
3. 分析本地项目的定位、架构、模块、核心机制及关键源码。
4. 先生成一份覆盖项目重要知识点、难度循序渐进的课程大纲。
5. 等待用户确认课程大纲，并根据反馈修改，直到获得确认。
6. 根据确认后的大纲，为每一节课生成独立的 Markdown 学习文件。
7. 让用户只阅读生成的课程文件，也能够逐步建立对项目技术架构和核心源码的系统认识。

## 4. 范围

### 4.1 本期范围

- 处理以本地项目目录为分析对象的开源项目学习需求。
- 读取和分析本地项目中的文档、目录结构和源码。
- 生成一份课程大纲 Markdown 文件。
- 在用户确认大纲后，生成与课程节数一致的分课 Markdown 文件。
- 支持由用户选择课程内容的语言。
- 支持用户指定学习目标、课程节数和输出目录。
- 在部分参数缺失时给出合理推荐或采用约定的默认输出目录。

### 4.2 本期不包含

- 不直接根据 GitHub 或其他远程仓库链接分析和生成课程。
- 自动部署或运行开源项目不是默认目标。
- 不默认要求用户完成环境搭建、动手实验或项目部署。
- 不在本阶段规定测验评分、学习进度跟踪、视频或演示文稿等额外产物。
- 本文档阶段只记录需求，不实现或安装 Skill。

如果项目的学习目标需要运行代码才能可靠解释关键机制，是否增加运行验证应在后续 Skill 设计阶段确定，不能默认为用户要求部署项目。

## 5. Skill 自身的编写要求

### REQ-001：Skill 使用英文编写

Skill 的指令、说明和配套规范文件必须使用英文编写。这里的“英文”指 Skill 自身的实现内容，不代表最终课程必须使用英文。

最终课程使用的语言由用户指定；用户未指定时，按照第 6 节进行澄清和推荐。

## 6. 调用时的需求澄清

Skill 被调用后，应先检查下列五项信息。需要用户补充或确认的信息应尽量在同一轮中集中提出，避免逐项反复追问。

### REQ-002：本地项目目录

- 检查用户是否已经提供需要学习的本地项目目录。
- 如果用户没有明确提供目录，但 Skill 当前运行在一个可识别的项目目录中，应将当前项目目录作为推荐值，请用户确认。
- 如果无法从当前环境确定目标项目目录，必须请用户补充本地路径。
- 必须确认该目录可读取，并包含可用于分析的项目文档或源码。
- 用户只提供远程仓库链接时，应请用户先下载项目并提供本地项目目录，不能直接根据远程链接生成课程。
- 在确定可用的本地项目目录前，不开始生成课程大纲或课程文件。

### REQ-003：课程语言

- 检查用户是否明确指定课程语言，例如中文或英文。
- 如果没有指定，应根据用户当前与 Agent 沟通所使用的主要语言推荐课程语言。
- 示例：用户主要使用中文沟通时，推荐中文；用户主要使用英文沟通时，推荐英文。
- 推荐结果需要向用户说明，并由需求澄清流程确定最终课程语言。

### REQ-004：课程节数

- 检查用户是否指定课程节数。
- 如果没有指定，应先结合项目规模、模块数量、架构复杂度和核心源码范围进行初步判断。
- Skill 应在 3 至 10 节范围内推荐一个具体节数，并简要说明推荐依据。
- 用户指定的节数优先于 Skill 的推荐。

### REQ-005：学习目标

- 检查用户是否明确说明希望通过课程达到的学习目标。
- 学习目标可以是理解技术架构和核心源码、准备二次开发、准备贡献代码或其他用户指定目标。
- 如果用户没有指定，默认推荐“只理解项目的技术架构和核心源码，不要求部署或运行项目”。
- Skill 应向用户说明推荐值，并允许用户接受或修改。
- 课程范围、内容深度、源码选择和课程顺序必须与最终确定的学习目标保持一致。

### REQ-006：输出目录

- 检查用户是否指定 Markdown 文件的输出目录。
- 如果用户已指定目录，使用用户指定的目录。
- 如果用户未指定目录，但当前存在项目工作目录，则在当前项目中创建一个课程输出文件夹。
- 默认文件夹名称格式为：`<open-source-project-name>-course`。
- 示例：项目名为 `langchain4j` 时，默认目录名为 `langchain4j-course`。
- 新建的默认课程目录在开始生成时应为空，用于承载本次大纲和课程文件。
- 如果目标输出目录已经存在且非空，按照 REQ-020 处理。

## 7. 项目分析与课程规划

### REQ-007：基于本地项目实际内容生成课程

课程内容必须建立在对本地项目目录的实际分析之上，包括但不限于项目文档、目录结构、主要模块、技术架构、核心流程和关键源码入口。不得只根据项目名称、远程仓库介绍或通用领域知识生成泛化课程。

### REQ-008：记录本地项目版本

- 生成课程前，应确定本次分析所依据的本地项目版本。
- 如果本地项目是 Git 仓库，应记录当前分支、Git Tag 或 Release（如存在）以及当前 Commit Hash。
- 如果工作区存在未提交修改，应在课程大纲中明确注明课程也基于这些本地修改生成，避免将其误认为对应 Commit 的原始内容。
- 如果本地目录不是 Git 仓库，应尝试从项目清单、版本文件或发布文档中确定版本；仍无法确认时，应明确标记为“本地快照，版本未知”，不得编造版本号。
- 课程大纲应在开头的项目信息中清楚写明版本，避免使用含糊的“最新版”表述。
- 所有课程文件必须基于同一个本地项目状态生成。

参考格式：

```text
项目版本：v1.2.0（Commit: abc1234）
本地状态：工作区干净
```

或：

```text
项目版本：main 分支（Commit: abc1234）
本地状态：包含未提交修改
```

### REQ-009：先生成课程大纲

完成需求澄清和必要的本地项目分析后，必须先生成一份课程大纲 Markdown 文件，并将其保存到最终输出目录。

大纲至少应包含：

- 项目名称；
- 本地项目目录；
- 项目来源地址（仅在能够从本地 Git 配置或项目文档中确认时记录）；
- 本次课程解读所依据的本地项目版本和工作区状态；
- 最终确定的学习目标；
- 课程总体学习目标；
- 课程设计原则或学习主线；
- 全部课程的编号、名称、核心问题和主要覆盖范围；
- 建议学习顺序；
- 每一课统一采用的内容结构；
- 必要时提供项目模块关系、学习地图或关键参考文档。

### REQ-010：大纲确认机制

- 课程大纲生成完成后，Skill 必须向用户报告大纲文件位置和课程概览，并请求用户确认。
- 在用户明确确认大纲前，不得生成完整的分课课程文件。
- 如果用户提出修改意见，应先更新课程大纲，再次请求确认。
- 只有在用户明确确认当前版本的大纲后，才能进入分课文件生成阶段。
- 分课文件的主题、顺序和数量必须以用户最终确认的大纲为准。
- 用户确认大纲后，不再重复执行项目初步调查、全项目分析、版本检查或工作区检查；只读取编写和验证各节课程所需的源码文件。

### REQ-011：知识点覆盖完整

课程大纲应覆盖理解该项目所需的重要知识点，重点包括：

- 项目要解决的问题与设计目标；
- 整体技术架构和组件边界；
- 核心模块及其职责；
- 关键数据模型、核心流程或生命周期；
- 重要实现机制和设计决策；
- 核心源码入口及跨模块调用链路；
- 适合作为总结的完整链路或整体回顾。

“覆盖完整”不要求逐文件讲解，而是不能遗漏会影响用户理解项目整体架构或核心实现的关键主题。具体课程组织方式由 Skill 根据项目实际结构和用户学习目标决定。

### REQ-012：课程循序渐进

课程应按照由浅入深的顺序组织。推荐的逻辑顺序为：

1. 项目背景、目标和整体认知；
2. 系统架构、组件边界和模块地图；
3. 核心概念、数据模型与基础机制；
4. 关键模块和核心源码；
5. 跨模块流程、设计权衡与完整链路；
6. 总结与综合理解。

具体顺序可根据项目特点调整，但后一课应尽量建立在前面课程已经介绍的概念之上。

## 8. 内容可验证性

### REQ-013：项目事实必须有本地证据

- 课程中的关键架构、模块职责、数据结构和执行流程必须能够对应到本地项目中的实际文档或源码。
- 讲解核心源码时，应尽量引用真实的相对文件路径，以及相关的类、函数、接口、配置项或其他代码符号。
- 课程中引用的文件、目录和代码符号应在生成时进行核对，不能引用本地项目中不存在的路径或符号。

### REQ-014：区分事实、推断与未知信息

- 源码或项目文档能够直接证明的内容，可以作为项目事实讲解。
- 根据代码结构得出的设计意图或架构判断，应明确使用“推断”“可以理解为”等表述，不能伪装成项目作者的明确结论。
- 无法从本地项目确认的信息必须如实说明，不得根据常见做法补写为该项目的实际实现。
- 如果项目文档与源码表现不一致，应指出差异，并以本次分析的本地源码状态作为课程解读基准。

### REQ-015：源码引用保持必要和准确

- 代码片段只截取解释当前机制所需的最小范围，避免大量复制项目源码。
- 代码解释必须与课程大纲中记录的本地项目版本和工作区状态一致。
- 生成完成后，应检查关键源码路径、代码符号和跨模块调用关系，修正能够发现的事实错误。

## 9. 分课文件生成

### REQ-016：按确认后的大纲生成全部课程文件

用户确认大纲后，按照最终大纲中确定的课程节数生成相同数量的独立 Markdown 文件。

例如，大纲包含 8 节课，则输出目录中应有：

- 1 个课程大纲文件；
- 8 个分课文件。

### REQ-017：每课以学习目标开篇

每个分课文件在标题之后，应首先给出本课学习目标。学习目标应明确说明用户学完本课后应该理解或能够解释的内容。

### REQ-018：每课以思考题收尾

每个分课文件的最后一个主要章节必须是“思考题”，用于检验用户是否理解本课的核心概念、设计原因和源码关系。

思考题不应只考查名词记忆，应优先引导用户解释设计选择、比较方案、追踪调用链路或推导系统行为。

### REQ-019：分课内容结构和独立可读性

参考现有 TencentDB Agent Memory 课程，每一课原则上包含：

1. 课程标题；
2. 学习目标；
3. 概念、机制或架构讲解；
4. 源码走读路线，包括相对项目根目录的真实路径和关键代码符号；
5. 关键设计决策或设计权衡；
6. 思考题。

每一课应围绕一个清晰主题展开，并给出理解该主题所需的上下文。课程之间可以相互引用，但不能只列源码路径或只给阅读清单而缺少解释。各项目可以根据主题增加必要的示例或对比表，但不能省略学习目标和思考题。

## 10. 输出目录与文件安全

### REQ-020：不得覆盖用户已有文件

- Skill 不得擅自覆盖、删除或清空用户已有的文件。
- 如果目标输出目录已经存在且非空，必须在写入大纲前向用户说明情况并询问如何处理。
- 在获得用户明确选择前，不得向该非空目录写入课程文件。
- 即使用户选择使用已有目录，也只能创建用户确认的新文件；存在同名文件时必须再次确认或使用用户同意的新名称。

### REQ-021：编号加章节名称

所有课程文件必须采用“数字编号 + 章节名称”的命名方式，并按照课程顺序排序。

参考格式：

```text
00_课程大纲.md
01_设计哲学与整体认知.md
02_系统拓扑与组件边界.md
...
10_团队权限模型与全链路串联.md
```

具体章节名称应与对应课程标题一致或保持明显对应关系。文件名应去除不适合作为文件名的字符。

### REQ-022：编号宽度

- 课程大纲使用 `00` 编号。
- 分课文件从 `01` 开始连续编号，不允许跳号或重复。
- 在当前 3 至 10 节课程范围内，统一使用两位数字，保证文件按名称排序时与学习顺序一致。

## 11. 默认执行流程

```text
用户调用 Skill
    ↓
检查本地项目目录、课程语言、课程节数、学习目标、输出目录
    ↓
集中澄清缺失信息，并给出语言、节数和学习目标推荐
    ↓
检查输出目录，避免覆盖用户已有文件
    ↓
分析本地项目文档、目录结构、源码和本地 Git 状态
    ↓
规划完整且循序渐进的课程结构
    ↓
生成 00_课程大纲.md
    ↓
请求用户确认大纲
    ↓
如有反馈则修改大纲，并再次请求确认
    ↓
用户确认后，按大纲生成 01...NN 的分课 Markdown 文件
    ↓
检查文件数量、编号、内容结构和源码证据
    ↓
向用户报告输出目录和文件清单
```

## 12. 验收标准

一次完整课程生成任务满足以下条件时，视为完成：

1. 已确定可读取的本地项目目录，并基于其中的实际文件进行分析。
2. 已确定课程语言、课程节数、学习目标和输出目录。
3. 未直接依赖远程仓库链接代替本地源码分析。
4. 对非空输出目录和同名文件进行了确认，没有擅自覆盖、删除或清空用户文件。
5. 输出目录中存在一个以 `00` 开头的课程大纲文件。
6. 大纲开头明确记录本地项目目录、版本、Commit Hash（如适用）和工作区状态。
7. 用户已经明确确认最终大纲，分课文件均在确认后生成。
8. 分课文件数量与最终大纲中的课程节数完全一致。
9. 分课文件从 `01` 开始连续编号，文件名包含章节名称。
10. 大纲覆盖项目的重要架构、模块、核心机制和源码学习路径。
11. 课程顺序由基础认知逐步过渡到核心源码和完整链路，并符合用户学习目标。
12. 每一课在标题后首先说明学习目标，最后一个主要章节为思考题。
13. 课程中引用的项目文件、目录和关键代码符号来自本地项目，并在生成时经过核对。
14. 项目事实与分析推断得到区分，无法确认的信息没有被编造为事实。
15. 用户确认大纲后没有重复执行项目调查、全项目分析、版本检查或工作区检查。
16. 所有课程内容均使用需求澄清阶段确定的课程语言。
17. Skill 自身使用英文编写。

## 13. 下一版本迭代方向

下一版本考虑增加 Mermaid 图表能力：

- 根据本地项目实际结构生成整体架构图或组件关系图；
- 根据核心源码生成关键调用链路图；
- Mermaid 图中的模块、节点和调用关系必须满足与正文相同的内容可验证性要求；
- 图表用于辅助理解，不替代正文中的机制讲解和源码走读路线。

该能力不属于当前版本的必需验收项。

## 14. 待后续设计确认的问题

以下事项不影响记录当前需求，但在正式实现 Skill 前需要进一步确定：

1. 用户指定的课程节数是否也必须限制在 3 至 10 节，还是仅默认推荐受此范围限制。
2. 用户指定的输出目录不存在时，是否直接创建。
